# Presentation, Live Demonstration and Viva Preparation

## 1. Five-minute presentation script

*(≈130 words per minute. Suggested slides in brackets.)*

**0:00 – Problem (slide: photos/icons of Wi-Fi, hostel, electricity issues)**
"Good morning. On our campus, problems like broken Wi-Fi, leaking taps or faulty
lights are reported on paper, by email or by word of mouth. Students never know
whether anyone is working on their complaint, and administrators have no single
place to see what is pending. My project solves this with a Smart Campus
Complaint Management System, and it also automates how the software is tested
and deployed to the cloud."

**0:40 – Solution (slide: two roles and the status lifecycle)**
"Students register, submit a complaint with a category and location, and track
it from Pending to In Progress to Resolved. Administrators see every complaint,
filter them, update the status with a note to the student, and see summary
statistics and charts."

**1:20 – Architecture (slide: architecture diagram)**
"The frontend is built with React. The backend is a single Node.js and Express
application that also serves the website. Data access goes through a database
adapter: the deployed app uses a JSON-file store, and a DynamoDB adapter with
indexed queries is also implemented and tested. The app is packaged as a Docker
container and runs on Render over HTTPS. I deliberately kept one backend instead of
microservices so the system stays simple to understand and maintain."

**2:00 – Security (slide: security table)**
"Passwords are hashed with bcrypt. After login, the server issues a signed token
stored in an httpOnly cookie, which JavaScript cannot read. Every protected API
checks the token and the role on the server, and a student can never read
another student's complaint, because the owner always comes from the verified
token. There is no default admin password; the first administrator is created
with a command-line script, or on the server from secret environment variables.
No secret is stored in the code: the token-signing key is generated by Render,
and the deploy credential is a GitHub encrypted secret."

**2:50 – CI/CD (slide: pipeline diagram)**
"Every push triggers GitHub Actions. Continuous integration runs 73 automated
tests, builds the frontend, builds the Docker image and smoke-tests the running
container. If anything fails, the pipeline stops. For the main branch,
continuous deployment then calls Render's deploy hook — a secret stored in
GitHub — so Render builds the same Dockerfile, and the pipeline waits until the
live health endpoint reports the exact commit that was tested. The Render
service itself is described as code in a render.yaml Blueprint."

**3:40 – Demo (switch to browser; see §2, short version)**

**4:30 – Results and conclusion (slide: results, limitations, future work)**
"*State your real results: number of tests passing, average pipeline duration
from your runs, the live URL working.* Limitations are that the free hosting
plan has no persistent disk, so data resets when the service restarts or sleeps,
and it sleeps after 15 idle minutes. Next steps are a managed database, email
notifications and image uploads. Thank you — I'm happy to take questions."

## 2. Live demonstration plan

**Before the session (30 minutes earlier)**
* [ ] Open `https://<your-app>.onrender.com/api/health` to wake the free instance (takes about a minute) — note the version.
* [ ] Remember that the free plan resets data on restart/sleep: create the demo data **after** waking it, and keep the site busy (refresh every few minutes) until the demo.
* [ ] Log in once as admin and as a demo student to confirm passwords.
* [ ] Prepare 3–4 complaints in different categories/statuses so charts look meaningful.
* [ ] Open tabs: live site (student, normal window), live site (admin, private window), GitHub Actions, Render dashboard (service Events and Logs).
* [ ] Prepare a tiny code change on a branch (e.g. landing page subtitle text).
* [ ] **Backup:** `docker compose up` running locally, plus screenshots and a screen recording of a full pipeline run, in case the network fails.

**Demo sequence (≈8–10 minutes when the panel allows a longer demo)**
1. Landing page → register a new student live.
2. Submit a complaint with an empty form (show validation), then a valid one (show success message, Pending badge).
3. Filter by category. Try `/admin` as the student → redirected.
4. Private window: log in as admin → cards and charts → filter Pending → Manage → set **In Progress** with a note.
5. Back in the student window, refresh → new status and note.
6. Render → service → **Logs** → search `complaint status updated` → show your update logged as JSON.
7. Render → **Events** → show the deploy history with commit SHAs and the health-checked switch-over.
8. Commit and push the prepared change (or merge its pull request) → show the pipeline running → explain the jobs while it runs.
9. When the deploy job finishes (3–10 min, so start step 8 early or show a recent run) → refresh the site → change is live; `/api/health` shows the new commit SHA.
10. Optional: show a pull request with a failing test that blocked deployment.

## 4. Key concepts in more depth

**Docker.** An *image* is a read-only package (OS libraries, Node.js, our code);
a *container* is a running instance of it. Our `Dockerfile` has two stages: the
first builds the React app, the second contains only production dependencies,
the backend and the built frontend, and runs as a non-root user. Benefits:
identical environment everywhere, small and reproducible.

**Render deployment.** Render reads `render.yaml`, builds our `Dockerfile`, and
runs the container with the `PORT` it provides (10000). Its proxy terminates
HTTPS, so the login cookie can be marked `Secure`. With a health check path set,
Render only switches traffic to a new version once `/api/health` answers, so a
broken build never replaces a working one. Auto-deploy is off: deployments are
started only by the pipeline's deploy hook call after the tests pass.

**Secrets.** A secret is anything that grants access: the JWT signing key, the
admin password and the deploy hook URL. None of them are in Git. Render generates
the JWT key, the admin password is typed into Render's dashboard, and the deploy
hook URL is a GitHub encrypted secret that is masked in logs.

**Free-plan trade-offs.** The free instance sleeps after 15 minutes without
traffic (the next request takes about a minute) and has no persistent disk, so
the JSON data file is recreated on every restart. That is why the admin account
is created automatically from environment variables at start-up.

**DynamoDB indexing.** Tables are queried by key. The `userId-createdAt-index`
answers "my complaints, newest first" directly, and the `status-createdAt-index`
answers "all Pending complaints". The admin's "all complaints" query asks the
three status partitions and merges results, so we never scan the whole table.

**Logging.** The app writes one JSON line per event to stdout. Docker captures
it and Render shows it in the service's Logs tab, where you can search for fields
like `"level":"error"`, `statusCode` or a `requestId`.

## 5. Common viva questions and answers

1. **Which database does the deployed app use, and why?** The built-in JSON-file
   adapter, because Render's free plan has no free durable database the data
   model can use. The code has a database adapter layer, so a DynamoDB adapter
   (designed with keys and indexes, tested with mocks and DynamoDB Local) can be
   switched on with one environment variable when a managed database is available.
2. **What is a GSI and why two?** An alternative key. One for "by student", one
   for "by status"; each serves a dashboard query without scanning.
3. **Why not a Scan for the admin list?** A Scan reads every item and costs grow
   with table size. Three small queries on the status index read only what is needed.
4. **How do you stop a student from seeing another student's complaint?** The user
   id comes from the signed token, not from the request. List queries use that
   id, and the single-complaint endpoint returns 404 unless you are the owner or an
   admin. Tests T23 and T26 prove it.
5. **Why 404 instead of 403 there?** So students cannot learn which complaint ids exist.
6. **Why store the token in a cookie and not localStorage?** An httpOnly cookie
   cannot be read by JavaScript, so an XSS bug cannot steal it.
7. **Then how do you prevent CSRF?** `SameSite=Strict` cookies are not sent from
   other sites, and state-changing requests must be JSON, which cross-site forms
   cannot send without a CORS preflight that the server refuses.
8. **How are passwords stored?** bcrypt hashes with a random salt; even the admin
   cannot see passwords.
9. **How is the first admin created?** Locally with `npm run create-admin` (the
   password is typed hidden). On Render, which has no shell on the free plan, from
   the secret `ADMIN_EMAIL`/`ADMIN_PASSWORD` environment variables at start-up;
   an existing account is never promoted. Registration can only create students.
10. **What is the difference between CI and CD?** CI automatically tests and
    builds every change; CD automatically deploys changes that passed CI.
    Here CI runs on all pushes/PRs; CD only on `main`.
11. **What happens if a test fails?** The `test` job exits non-zero, later jobs
    don't start, and nothing is deployed. The PR shows a red cross.
12. **How does GitHub trigger the deployment securely?** It sends a request to
    Render's deploy hook URL, which is stored as an encrypted GitHub secret,
    masked in logs, and only used by the deploy job on `main` in the
    `production` environment.
13. **Why does Render build the image instead of GitHub pushing it?** It keeps the
    setup free and simple (no image registry or credentials). The same
    `Dockerfile` is built and smoke-tested in CI first, and the pipeline verifies
    that the live app reports exactly the tested commit.
14. **How do you know the deployment worked?** The pipeline polls `/api/health`
    until it returns the new commit SHA (Render provides it as
    `RENDER_GIT_COMMIT`), then checks `/api/health/ready` and the homepage.
15. **What if the new version is broken?** Render keeps the old version serving
    traffic until the new one passes its health check, and the pipeline job fails
    with a pointer to the Render logs. You can roll back to an earlier deploy from
    Render's Events page, or push a fix/revert through the same tested pipeline.
16. **Difference between `/api/health` and `/api/health/ready`?** Liveness (the
    process responds) vs. readiness (it can also reach its data store). Render
    uses the cheap one; the pipeline checks both.
17. **Where are the logs and what is in them?** Render's Logs tab; JSON lines with
    timestamp, level, request id, method, path, status code, duration and user
    id — never passwords or request bodies.
18. **Why Render instead of AWS, Azure or a VPS?** Render builds a Dockerfile
    directly, provides HTTPS, a public URL, health checks and logs, and has a
    free plan without a credit card — the AWS account could not be verified.
    The app is a standard Docker container, so it can move to another host.
19. **What are the limits of the free plan?** It sleeps after 15 idle minutes
    (cold start about a minute), has no persistent disk (data resets on
    restart, redeploy or sleep), no shell, and 750 instance hours a month.
20. **What does `render.yaml` give you?** Infrastructure as code: the service
    configuration is versioned and reviewable, and can be recreated identically.
21. **How do you handle secrets?** The JWT key is generated by Render
    (`generateValue`), the admin password is entered in Render (`sync: false`),
    the deploy hook URL is a GitHub encrypted secret; `.env` files are git-ignored.
    Improvement: a dedicated secrets manager and rotating the admin password.
22. **What is least privilege, and where did you apply it?** Give each identity
    only the permissions it needs: students can only reach their own complaints,
    only admins reach admin routes, the container runs as a non-root user, and the
    deploy hook can only redeploy `main`, not change code or settings.
23. **How does the app work locally without a cloud account?** A local database adapter with
    the same interface stores data in a JSON file; Docker Compose can also run
    DynamoDB Local.
24. **How do your tests avoid touching AWS?** In-memory database for API tests,
    and a mocked AWS SDK client for the DynamoDB adapter tests.
25. **What would you change for 10,000 users?** A managed database (e.g. the
    existing DynamoDB adapter), a paid instance with several replicas, pagination,
    pre-computed statistics counters, a category index, a secrets manager,
    alerting, and a CDN for static assets.

## 7. Limitations and future improvements

**Limitations**
* Render free plan: no persistent disk, so all data resets on restart, redeploy or spin-down.
* Free instance sleeps after 15 minutes without traffic; first request then takes about a minute.
* Single instance: no automatic failover.
* No email/SMS notifications; students must log in to see updates.
* No file or photo attachments.
* No password reset, email verification or account management.
* Lists are capped at 1,000 items per query and not paginated in the UI.
* Statistics are computed on request by reading all complaints (fine at campus scale).
* Tokens cannot be revoked before expiry; the rate limiter is in-memory.
* Frontend has no automated UI tests (verified manually and by API tests).

**Future enhancements**
* Permanent storage: paid Render instance with a persistent disk (no code change), or a managed database through the adapter layer.
* Custom domain on Render.
* Email notifications on status change.
* Photo attachments in object storage with pre-signed upload URLs.
* Password reset and email verification; optional college SSO.
* Complaint comments/history timeline and priority levels; assignment to departments/staff.
* Pagination and search; a category index; pre-computed statistics.
* A dedicated secrets manager; uptime monitoring and alerting.
* Frontend tests (Vitest + Testing Library) and end-to-end tests (Playwright) in CI.
* Staging environment with manual approval before production.
