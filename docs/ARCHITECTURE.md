# Architecture and Design Decisions

## 1. System overview

```
 Browser (student/admin)          Render (free web service, region: Singapore)
   │  HTTPS                      ┌─────────────────────────────────────────────────────────┐
   └────────────────────────────▶│ Render proxy (TLS) ──▶ Docker container  :$PORT (10000)  │
                                 │                        Node.js / Express                 │
                                 │                        ├─ /api/*  REST API               │
                                 │                        └─ /*      built React app        │
                                 │                        JSON-file database /app/data      │
                                 │                        (reset on restart on free plan)   │
                                 │  stdout/stderr ──▶ Render Logs · /api/health ──▶ Events  │
                                 └───────────────▲─────────────────────────────────────────┘
                                                 │ builds Dockerfile from main
 GitHub Actions ── tests pass ── POST deploy hook┘ ── then polls /api/health for the new commit
```

There is **one** backend application (no microservices). Express serves both the
REST API under `/api` and the compiled React app, so the browser talks to a
single origin. That removes the need for CORS and lets the login cookie use
`SameSite=Strict`.

## 2. Request flow (example: a student submits a complaint)

1. React (`NewComplaint.jsx`) validates the form and calls `POST /api/complaints` with a JSON body.
2. The browser automatically attaches the `scc_token` httpOnly cookie.
3. Express middleware runs in order: security headers (helmet) → CORS (deny by
   default) → JSON body parser (20 KB limit) → cookie parser → request logger →
   "JSON only" check for state-changing requests.
4. `requireAuth` verifies the JWT signature and expiry; `requireRole('STUDENT')` checks the role.
5. `validateComplaint` checks every field on the server.
6. The route builds the complaint (UUID, owner = user id **from the token**, status `PENDING`, timestamps).
7. The database adapter writes it (JSON file by default; DynamoDB `PutItem` when `DB_DRIVER=dynamodb`).
8. A structured log line is written; the response is `201 Created`.

## 3. Key design decisions (beginner-friendly explanations)

| Decision | Why |
| --- | --- |
| **React + Vite** | Vite gives a fast development server and builds optimised static files that Express can serve. |
| **Express serves the frontend** | One container, one URL, no CORS. Simpler to deploy and explain than a separate static-site host. |
| **JSON-file database on Render, DynamoDB adapter kept** | Render's free plan offers no free durable storage that the existing data model can use, so the built-in JSON-file adapter is used. The DynamoDB adapter (same interface, indexed queries) stays available and tested for a future cloud database. |
| **Database adapter pattern** (`db/localStore.js`, `db/dynamoStore.js`) | Both adapters expose the same functions. Switching storage is one environment variable (`DB_DRIVER`); tests use an in-memory copy and never touch real data. |
| **JWT in an httpOnly cookie** | Stateless sessions (no session table), and JavaScript cannot read the token, which limits the damage of an XSS bug. |
| **Docker** | The same `Dockerfile` runs on a laptop, in GitHub Actions and on Render: "works on my machine" problems disappear. |
| **Render (Docker runtime)** | Free web hosting that builds a `Dockerfile` directly, provides HTTPS and a public URL, health checks and logs, with no credit card for the free path and no servers to manage. |
| **Deploy hook + `autoDeployTrigger: off`** | Render only deploys when GitHub Actions calls the hook, which happens only after every test and the container smoke test passed. |
| **`render.yaml` Blueprint** | The service configuration (Docker, region, health check, environment variables) is stored as code in the repository, so it is repeatable and reviewable. |
| **Secrets outside Git** | `JWT_SECRET` is generated by Render, the admin password is entered in Render, and the deploy hook URL is a GitHub encrypted secret. |
| **Plain CSS and a hand-made bar chart** | Fewer dependencies to learn and maintain; the dashboard only needs simple comparisons. |

## 4. CI vs CD

| | Continuous Integration (CI) | Continuous Deployment (CD) |
| --- | --- | --- |
| **Goal** | Prove that every change still works | Automatically release changes that passed CI |
| **When** | Every push and every pull request | Pushes to `main` only, after CI passed and once Render is configured |
| **Jobs** | `test` (backend tests, frontend build), `docker` (image build + smoke test) | `deploy` (Render deploy hook, wait for new version, live health check) |
| **Credentials** | None | The deploy hook URL, stored as a GitHub secret, only used in the `production` environment |
| **If it fails** | The pull request shows a red ❌; nothing is deployed | Render keeps the previous version running; the job fails and points to the Render logs |

## 5. What is automated vs. manual

| Task | Without automation | In this project |
| --- | --- | --- |
| Running tests | Developer remembers to run them | Every push/PR, merge blocked visually when red |
| Building the app | Manual `npm run build` | CI builds frontend and Docker image |
| Packaging | Manually zip/copy files to a server | Docker image built and smoke-tested by CI, then built by Render from the same `Dockerfile` |
| Deploying | Upload in the console, click deploy | `git push` to `main` → automatic deploy |
| Verifying | Open the site and hope | Pipeline checks `/api/health` reports the new commit SHA, then `/api/health/ready` and the homepage |
| Creating hosting resources | Click through settings by hand | Render Blueprint (`render.yaml`) |
| Creating the admin | Run a script on the server | Created at start-up from secret environment variables |
| Logs | SSH into the server | Collected by Render automatically |
| **Still manual (once)** | | Render account, applying the Blueprint, one GitHub secret + one variable + the `production` environment |

## 6. Phase-by-phase implementation summary

| Phase | Files | How to verify |
| --- | --- | --- |
| 1. Architecture and requirements | `README.md`, `docs/ARCHITECTURE.md`, `docs/DATABASE.md` | Read through; matches the requirements table in the report outline |
| 2. Frontend | `frontend/**` | `cd frontend && npm run build` succeeds; `npm run dev` shows the landing page |
| 3. Backend and local database adapter | `backend/src/app.js`, `server.js`, `config.js`, `logger.js`, `db/*` | `npm run dev`, then `curl localhost:8080/api/health` |
| 4. Auth, authorization, complaints | `backend/src/middleware/auth.js`, `routes/*`, `validation.js`, `scripts/create-admin.js` | Register/login in the UI; student cannot open `/admin`; API returns 403 for students on admin routes |
| 5. Automated tests | `backend/tests/*` | `cd backend && npm test` → all suites pass |
| 6. Containerization | `Dockerfile`, `.dockerignore`, `docker-compose.yml`, `backend/scripts/create-tables.js` | `docker build` / `docker run` or `docker compose up --build`, open http://localhost:8080 |
| 7. Cloud deployment (Render) | `render.yaml`, `backend/src/bootstrapAdmin.js` | Follow `docs/RENDER_DEPLOYMENT.md`; service shows **Live** |
| 8. GitHub Actions CD | `.github/workflows/ci-cd.yml` | Push to `main`; all three jobs green |
| 9. Health checks and monitoring | `routes/health.js`, `middleware/requestLogger.js`, `healthCheckPath` in `render.yaml` | `/api/health`, `/api/health/ready`; Render Logs and Events |
| 10. Documentation and presentation | `docs/*` | Use for report, demo and viva |

**Outstanding configuration you must do yourself:** Render account, applying
the Blueprint (with the admin email and password), the GitHub secret
`RENDER_DEPLOY_HOOK_URL`, the variable `RENDER_APP_URL` and the `production`
environment. All steps are in [RENDER_DEPLOYMENT.md](RENDER_DEPLOYMENT.md).
